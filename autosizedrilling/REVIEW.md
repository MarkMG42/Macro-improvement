# Статическая проверка AutoSizeDrilling

Дата: 28 октября 2026 года.

Проверена именно приложенная DLL: логика класса `AutoSizeDrilling.AutoSizeDrill` прочитана декомпилятором ILSpy 9.1.0.7988. Исходный язык — VB.NET; декомпилятор представил код на C#. Имена методов ниже взяты из сборки. PDB содержит ссылки на исходные файлы `AutoSizeDrill.vb` и другие файлы проекта; сам исходный проект не предоставлен.

Бинарные файлы не изменялись. SolidWorks в этой Linux-среде отсутствует; проверки на реальном чертеже не проводились. Изложенные ниже условия найдены в алгоритме, но без проблемного чертежа нельзя установить, какое из них объясняет наблюдавшуюся пользователем ошибку.

## 1. Количество и диаметр отверстий: подтверждённое ограничение алгоритма

`GetUniqueX` оставляет только первое отверстие на каждую координату X с допуском `0.00005` м на листе. Различия Y и радиуса здесь не учитываются. Затем `AddDimensions` вызывает:

```csharp
CreateDiameterDimension(uniqueX[0], uniqueX.Count, yTop + 0.01);
```

В `CreateDiameterDimension` размер создаётся по ребру только этого первого отверстия, а перед ним добавляется текст `count + " X "`. Проверки одинаковых диаметров нет.

Следствия:

- Для шести отверстий в двух рядах по три одинаковых X получится подпись `3 X`, если все шесть рёбер распознаны: это число позиций X, а не число отверстий.
- Для трёх отверстий с разными X и диаметрами 8, 10, 12 мм будет одна подпись `3 X` при размере первого отверстия. Остальные диаметры не будут отражены.
- Из нескольких отверстий с одним X выбирается первое в порядке перечисления геометрии, до сортировки по X. По этому же представителю создаётся размер до отверстия; поперечный размер создаётся только для `uniqueX[0]`. Разные ряды по Y отдельно не размеряются.

При одном ряде одинаковых отверстий это ограничение может не проявляться. В отдельной будущей правке стоит разделить набор позиций для линейных размеров и группы отверстий по диаметру/ряду для подписей.

## 2. Круговая кривая автоматически считается отверстием

`GetEdges` проверяет `curve.IsCircle()`, затем `GetHole` использует центр и радиус из `CircleParams`. Ни замкнутость ребра, ни тип соседних граней, ни направление оси окружности относительно вида не проверяются. `FilterHoles` проверяет только попадание центра внутрь прямоугольных границ.

Это позволяет принять за отверстие круговое ребро наружного элемента, дугу скругления или другую круговую геометрию с подходящим центром. Одного `IsCircle()` недостаточно, чтобы отличить полную окружность от ребра-дуги на круговой кривой. Выходы отверстия, зенковки и концентрические рёбра разных радиусов также не распознаются как один технологический элемент: `AddUniqueHole` сравнивает X, Y и радиус, а `GetUniqueX` позже оставляет только первое ребро по X. Возможный результат — выбор диаметра зенковки вместо отверстия или размер по постороннему ребру.

Это кандидаты для воспроизведения в SolidWorks, а не утверждение, что любая дуга обязательно попадёт в результат.

## 3. Габариты определяются по осям листа и прямолинейным рёбрам

В `FindBounds` нижняя/верхняя границы выбираются только из почти горизонтальных рёбер, левая/правая — только из почти вертикальных. Проверяется разность координат концов после преобразования в вид, с абсолютным допуском `0.00005` м.

Поворот вида, косой торец, фаска или вырез могут привести к отсутствию нужной границы либо выбору внутреннего ребра вместо реального крайнего контура. Проверка успеха требует только четырёх ненулевых ссылок: проверки прямоугольности профиля или принадлежности границ одной детали нет. В сборочном виде `GetEdges` собирает рёбра всех видимых компонентов, поэтому крайние рёбра могут относиться к разным деталям.

Это объясняет, почему алгоритм может корректно работать на простом ортогональном виде и ошибаться на отдельных профилях или сборочных видах.

## 4. Тип создаваемого линейного размера не зафиксирован

`CreateLinearDimension` выбирает два ребра и вызывает универсальный `swModel.AddDimension2(x, y, 0)`. Отдельные вызовы для горизонтального/вертикального размера отсутствуют; тип и фактические привязки результата не проверяются. Для пары «прямое ребро — круговое ребро» не задано явно условие измерения до центра окружности.

Это потенциальная зависимость от геометрии и поведения API/настроек SolidWorks. На проблемном чертеже нужно проверить, отложен ли размер до центра отверстия или до касательной, и какие именно рёбра выбраны. Утверждать по одной DLL, что причина именно в этом, нельзя. Рассчитанные X/Y используются для размещения текста; само значение размера определяет SolidWorks по выбранным объектам.

## 5. Допуск зависит от масштаба вида

`TOL = 0.00005` применяется к координатам после `ModelToViewTransform`, то есть к метрам на листе, без нормализации масштаба. В пересчёте на модель это 0.05 мм при 1:1, 0.5 мм при 1:10 и 5 мм при 1:100. Поэтому при сильном уменьшении могут слиться близкие позиции X или отсеяться центры около границы. Это относится к распознаванию и фильтрации, а не доказывает неверное масштабирование самого размерного значения.

## Что проверено и что остаётся

- Извлечены методы распознавания, фильтрации, преобразования координат и создания размеров; проверены вызовы из точки входа.
- На синтетических данных отдельно воспроизведено правило `GetUniqueX`: два ряда по три позиции дают три представителя; разные диаметры по разным X не разделяются. Это проверка алгоритма, не запуск макроса.
- SHA-256 копий сверены с четырьмя загруженными файлами.
- Проверка размеров в SolidWorks, совместимости версии и загрузки VSTA не выполнялась.

Для точного диагноза следующая полезная проверка — один чертёж с ошибкой: выбранный вид, масштаб, связанные модели, ошибочное значение и ожидаемая привязка. До этого менять рабочую сборку не требуется.
